# DEEPFORGE: IDLE EMPIRE
## Master Game Design Document / Technical Design Document
### Версия 0.1 — браузерная mobile-first idle/tycoon игра

---

# 1. Концепция

**Рабочее название:** DEEPFORGE: Idle Empire.

Название временное и может быть заменено перед релизом без изменения архитектуры.

Жанр:

- Idle / Incremental.
- Tycoon.
- Management.
- Resource management.
- Коллекционная мета-прогрессия.
- Live Ops.
- Соревновательные события.

Основная идея:

Игрок получает небольшой промышленный объект и постепенно превращает его в огромную глобальную добывающую корпорацию.

Основной цикл:

**добыча → транспортировка → переработка/продажа → деньги → улучшения → автоматизация → новые уровни → новая локация → новая зона → престиж → глобальные улучшения → события → соревнования.**

Игра должна хорошо работать короткими сессиями по 30–120 секунд и длинными активными сессиями по 10–30 минут.

Игрок должен постоянно видеть:

- движение работников;
- движение грузов;
- рост чисел;
- изменение производительности;
- визуальное развитие объекта;
- новые механики;
- новые территории;
- новые персонажи;
- новые награды.

# 5. Основная сцена объекта

Каждая добывающая площадка состоит из трех глобальных компонентов:

### A. Excavation Decks

Подземные уровни добычи.

На каждом:

- рабочие;
- источник ресурса;
- склад уровня;
- начальник;
- уровень;
- производительность;
- улучшение;
- способность;
- текущий накопленный ресурс.

### B. Cargo Lift

Вертикальная транспортировка.

Лифт:

1. спускается;
2. забирает ресурс;
3. поднимается;
4. выгружает его наверху.

Имеет параметры:

- вместимость;
- скорость;
- время загрузки;
- количество груза за цикл;
- уровень;
- начальник.

### C. Logistics Hub

Наземная логистика.

Работники:

1. получают ресурс у лифта;
2. несут его на склад/переработку;
3. превращают ресурс в деньги.

Параметры:

- вместимость;
- скорость;
- число работников;
- время цикла;
- уровень;
- начальник.

# 6. Главная экономическая механика

Игра должна реально рассчитывать производственную цепочку.

Нельзя просто показывать декоративных рабочих.

Для шахты `i`:

`Production_i = Workers × CarryCapacity × CyclesPerSecond × Multipliers`

Общее производство:

`TotalShaftProduction = Σ Production_i`

Пропускная способность лифта:

`LiftThroughput = LiftCapacity × LiftCyclesPerSecond × Multipliers`

Пропускная способность логистики:

`HubThroughput = CarrierCapacity × CarrierCyclesPerSecond × Carriers × Multipliers`

Фактическая базовая производительность предприятия:

`EffectiveThroughput = MIN(TotalShaftProduction, LiftThroughput, HubThroughput)`

Доход:

`IncomePerSecond = EffectiveThroughput × ResourcePrice × GlobalMultipliers`

Это создаёт главный игровой выбор:

**что является узким местом?**

Например:

Добыча:
120M/s

Лифт:
75M/s

Логистика:
100M/s

Итоговая эффективная производительность:

**75M/s**

UI должен явно помогать игроку замечать bottleneck.

# 7. Активная симуляция

Пока объект открыт, ресурс реально существует в буферах.

Пример:

`ShaftBuffer[1]`

`ShaftBuffer[2]`

`ShaftBuffer[3]`

Лифт физически забирает ресурс из них.

После этого ресурс:

`LiftCargo → SurfaceBuffer → Logistics → Cash`

Поэтому визуальные анимации и экономика соответствуют друг другу.

# 8. Idle-режим

Когда игрок выходит:

не нужно симулировать каждую секунду.

Сохраняются:

- timestamp;
- текущая производительность;
- все активные постоянные множители;
- разрешённая продолжительность offline income.

При возврате:

`OfflineTime = CurrentTime - LastSaveTime`

`OfflineReward = IdleIncomePerSecond × OfflineTime × OfflineMultiplier`

Должно появляться окно:

**«Пока вас не было»**

Показывает:

- время отсутствия;
- заработанные деньги;
- применённые бонусы.

# 9. Большие числа

Обязательно использовать специализированную библиотеку больших чисел.

Рекомендуется:

**break_infinity.js**

или аналог.

Нельзя использовать обычный JS `Number` для всей экономики.

Формат:

1K  
1M  
1B  
1T  
1aa  
1ab  
1ac  
…

Система форматирования централизованная.

# 10. Улучшения

Каждый объект имеет уровень.

Стоимость:

`Cost(level) = BaseCost × Growth^Level × LocationModifier`

Покупка:

- +1;
- +10;
- +25;
- MAX.

Bulk-покупка должна рассчитываться математически, а не циклом по 1000 раз.

# 11. Milestones

На определённых уровнях происходят скачки мощности.

Например:

10  
25  
50  
100  
200  
…

Это не окончательные значения.

Все milestones находятся в конфиге.

Пример:

```text
level: 100
productionMultiplier: 2
workersVisualUpgrade: true
```

После milestone игрок должен визуально ощущать прогресс.

# 12. Барьеры

3. начинается таймер;
4. после окончания открываются следующие уровни.

Варианты ускорения:

- специальная валюта;
- предмет;

- rewarded-реклама;
- событийный бонус.

Начальники бывают трех типов:

- Excavation;

Обычные начальники дают:

- скорость;

- увеличение производительности.

# 14. Specialists

Аналог глубокой системы уникальных менеджеров, но со своими персонажами.

Название:

**Specialists.**

Каждый Specialist:

- уникальный персонаж;
- редкость;
- специализация;
- уровень;
- ранг;
- активный навык;
- пассивный навык;
- affinity;
- экипировка.

Редкости:

- Common;
- Rare;
- Epic;
- Legendary;
- Mythic — можно оставить резервом для будущего.

Пример:

**Mara Vex — Lift Specialist**

Active:

на 30 секунд увеличивает скорость лифта ×8.

Passive:

+10% вместимости всех Lift в текущей зоне.

# 21. Prestige

Название нашей механики:

**Rebuild.**

Игрок сбрасывает выбранный объект.

Сбрасываются:

- этажи;
- базовые уровни;
- местные начальники;
- барьеры.

Сохраняются:

- Specialists;
- Research;
- Collection;
- глобальная валюта;
- permanent upgrades.

Взамен:

объект получает постоянный множитель дохода.

Пример:

`Rebuild I → ×2.1`

`Rebuild II → ×4.8`

Значения не копировать из референса.

**Corporate Relics.**

# 24. Collection

**Crew Collection.**

# 25. Academy

Отдельная зона карты.

Аналог отдельной progression-системы для Specialists.

Название:

**Academy Operations.**

Это серия относительно коротких объектов.

За прохождение игрок получает:

- зелёный ресурс — recruitment;
- синий — levels;
- красный — promotions.

Academy состоит из десятков уровней.

Контент должен быть data-driven, поэтому можно создать 10, 50 или 300 уровней без изменения игрового движка.

# 36. Stars / Skip

После прохождения Endless Descent определяется скорость прохождения.

1 Star:
обычное прохождение.

2 Stars:
разрешить пропустить 1 следующий объект.

3 Stars:
разрешить пропустить 2.

За пропущенный контент игрок получает базовый progression reward.

Система ускоряет прохождение опытными игроками.

# 56. Leaderboard security

Нельзя доверять клиенту значение:

`score = 999999999`

Клиент отправляет действия.

Сервер проверяет:

- event active;
- session valid;
- upgrade possible;
- currency sufficient;
- timestamp valid;
- action sequence valid.

Сервер сам обновляет score.

Competitive events должны быть преимущественно server-authoritative.

# 57. Clock cheating

Основная idle-игра может работать offline.

Но:

- leaderboard;
- event timers;
- tickets;
- rewards

используют **server time**.

Перевод часов телефона не должен позволять получать рейтинговые преимущества.

- lazy loading;
- asset bundles;
- LOD;
- ограничение particle count.

Не создавать сотни DOM-элементов для рабочих.

Рабочие находятся внутри Canvas.

# 59. Adaptive quality

При первом запуске провести лёгкий benchmark.

Режимы:

LOW  
MEDIUM  
HIGH

LOW:

- меньше particles;
- меньше workers;
- упрощённые shadows;
- меньше animation FPS.

HIGH:

- full FX;
- больше workers;
- ambient particles;
- дополнительные lighting effects.

Экономика не зависит от количества отображаемых workers.

Разработчик не имеет права писать:

«готово»

1. работает логика;
2. работает UI;
3. сохранение работает;
4. после refresh состояние корректно;
5. mobile работает;
6. tablet работает;
7. desktop работает;
8. ошибки обработаны;
9. добавлен тест;
10. обновлён changelog.

# 70. Приоритет разработки

Всегда:

**механика → данные → сохранение → backend → UI → временная графика → тест → финальная графика.**

Не наоборот.

Нельзя сначала потратить неделю на красивые шахты, а потом обнаружить, что экономика требует другой структуры.

# 71. Правила для AI-разработчика

1. Не спрашивать подтверждение перед каждым этапом.

2. Выполнять этапы по порядку.

3. Не переписывать уже работающую систему без необходимости.

4. Перед изменением анализировать зависимости.

5. Mobile-first.

6. Все новые экраны проверять на 360 px.

7. Код TypeScript.

8. Комментарии в коде на русском.

9. Экономические параметры не хардкодить в компонентах.

10. Использовать конфиги.

11. После каждого этапа обновлять `CHANGELOG.md`.

12. После крупного этапа создавать резервную рабочую версию.

13. Не использовать временные заглушки там, где они влияют на механику.

14. Графические placeholder допустимы до Art Pass.

15. Не начинать следующий этап с красными тестами.

# 6. Главная экономическая механика

Игра должна реально рассчитывать производственную цепочку.

Нельзя просто показывать декоративных рабочих.

Для шахты `i`:

`Production_i = Workers × CarryCapacity × CyclesPerSecond × Multipliers`

Общее производство:

`TotalShaftProduction = Σ Production_i`

Пропускная способность лифта:

`LiftThroughput = LiftCapacity × LiftCyclesPerSecond × Multipliers`

Пропускная способность логистики:

`HubThroughput = CarrierCapacity × CarrierCyclesPerSecond × Carriers × Multipliers`

Фактическая базовая производительность предприятия:

`EffectiveThroughput = MIN(TotalShaftProduction, LiftThroughput, HubThroughput)`

Доход:

`IncomePerSecond = EffectiveThroughput × ResourcePrice × GlobalMultipliers`

Это создаёт главный игровой выбор:

**что является узким местом?**

Например:

Добыча:
120M/s

Лифт:
75M/s

Логистика:
100M/s

Итоговая эффективная производительность:

**75M/s**

UI должен явно помогать игроку замечать bottleneck.

# 7. Активная симуляция

Пока объект открыт, ресурс реально существует в буферах.

`ShaftBuffer[2]`

`ShaftBuffer[3]`

Лифт физически забирает ресурс из них.

`LiftCargo → SurfaceBuffer → Logistics → Cash`

Поэтому визуальные анимации и экономика соответствуют друг другу.

# 8. Idle-режим

Когда игрок выходит:

не нужно симулировать каждую секунду.

Сохраняются:

- timestamp;
- текущая производительность;
- все активные постоянные множители;
- разрешённая продолжительность offline income.

При возврате:

`OfflineTime = CurrentTime - LastSaveTime`

`OfflineReward = IdleIncomePerSecond × OfflineTime × OfflineMultiplier`

Должно появляться окно:

**«Пока вас не было»**

Показывает:

- время отсутствия;
- заработанные деньги;
- применённые бонусы.

# 36. Stars / Skip

После прохождения Endless Descent определяется скорость прохождения.

3 Stars:
разрешить пропустить 2.

За пропущенный контент игрок получает базовый progression reward.

Система ускоряет прохождение опытными игроками.

# 56. Leaderboard security

Нельзя доверять клиенту значение:

`score = 999999999`

Клиент отправляет действия.

Сервер проверяет:

- event active;
- session valid;
- upgrade possible;
- currency sufficient;
- timestamp valid;
- action sequence valid.

Сервер сам обновляет score.

Competitive events должны быть преимущественно server-authoritative.

# 57. Clock cheating

Основная idle-игра может работать offline.

Но:

- leaderboard;
- event timers;
- tickets;
- rewards

используют **server time**.

Перевод часов телефона не должен позволять получать рейтинговые преимущества.

- музыку;
- звуки;
- тексты;
- баланс;
- точные цены;
- точные награды;
- точные таблицы progression;
- UI screenshots как финальный дизайн.

Референс используется для понимания **системной архитектуры и жанровой глубины**.

---

# 69. Definition of Done для каждой задачи

Разработчик не имеет права писать:

«готово»

если функция только нарисована.

Функция считается готовой только если:

1. работает логика;
2. работает UI;
3. сохранение работает;
4. после refresh состояние корректно;
5. mobile работает;
6. tablet работает;
7. desktop работает;
8. ошибки обработаны;
9. добавлен тест;
10. обновлён changelog.

---

# 70. Приоритет разработки

Всегда:

**механика → данные → сохранение → backend → UI → временная графика → тест → финальная графика.**

Не наоборот.

Нельзя сначала потратить неделю на красивые шахты, а потом обнаружить, что экономика требует другой структуры.

---

# 71. Правила для AI-разработчика

1. Не спрашивать подтверждение перед каждым этапом.

2. Выполнять этапы по порядку.

3. Не переписывать уже работающую систему без необходимости.

4. Перед изменением анализировать зависимости.

5. Mobile-first.

6. Все новые экраны проверять на 360 px.

7. Код TypeScript.

8. Комментарии в коде на русском.

9. Экономические параметры не хардкодить в компонентах.

10. Использовать конфиги.

11. После каждого этапа обновлять `CHANGELOG.md`.

12. После крупного этапа создавать резервную рабочую версию.

13. Не использовать временные заглушки там, где они влияют на механику.

14. Графические placeholder допустимы до Art Pass.

15. Не начинать следующий этап с красными тестами.

# 73. Основная UX-идея

На каждом экране игрок должен понимать:

**Что сейчас производится?**

**Сколько я получаю?**

**Что мешает получать больше?**

**Что я могу улучшить?**

**Что откроется следующим?**

Если ответ скрыт в пяти меню — UI плохой.

---

# 74. Главный психологический цикл

Игрок должен постоянно получать чередование:

маленькая награда → улучшение → визуальное ускорение → большая награда → новая механика → новая территория → reset → резкое ускорение → новый долгосрочный goal.

Именно это должно держать игру месяцами и годами.

# 75. MASTER COMMAND ДЛЯ ДРУГОЙ НЕЙРОНКИ

Использовать весь этот документ как главный источник требований.

Начать с:

**ЭТАП 0 — FOUNDATION.**

Не пытаться реализовать всю игру одним файлом.

Создавать production-ready архитектуру, рассчитанную на дальнейшие этапы.

После каждого этапа:

1. проверить desktop;
2. проверить tablet;
3. проверить mobile;
4. проверить сохранения;
5. исправить ошибки;
6. обновить CHANGELOG;
7. сообщить:
   - что сделано;
   - какие файлы созданы;
   - какие механики работают;
   - какие тесты проведены;
   - что является следующим этапом.

Главное правило:

**каждый этап обязан оставлять после себя полностью запускаемую рабочую игру.**

После завершения одного этапа переходить к следующему только из этого GDD и не менять архитектуру хаотично.

Конечная цель:

создать самостоятельную браузерную idle/tycoon игру уровня полноценного коммерческого продукта с глубиной систем, сопоставимой с крупными многолетними mobile idle-проектами, но с полностью собственным миром, дизайном, персонажами, балансом и графикой.
